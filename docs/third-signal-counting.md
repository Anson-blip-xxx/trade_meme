# 第三次信号计数与永久防重

首页和 Telegram 的“启动计数”共同控制第三次通知实盘策略。服务配置为实盘模式后，本人点击启动，才建立新的实盘计数批次；后续达标信号经开仓核验后自动提交买单，并随买单附加配置的止盈止损。点击“停止计数”后，不再接收新的计数与买入触发，已有持仓监控、保护单和成交查询继续运行。停止不撤销已经提交的平台订单。

状态中的 `mode=live` 表示当前策略模式，`executionEnabled=true` 才表示本轮允许实盘触发。实盘配置但尚未启动时，`executionEnabled=false` 是正常状态。旧模拟批次不会因改配置变成实盘批次，旧通知和候选不会补发买单；需要本人发出新的启动指令。已启动的实盘批次在普通服务重启后保留，未知提交只核对结果，不重复下单。页面仍兼容明确标为 `mode=simulation` 的研究模式。

部署配置：

```dotenv
ENTRY_MODE=off
THIRD_SIGNAL_EXECUTION_MODE=live
SCANNER_CHAINS=solana
ENTRY_BALANCE_BPS_SOLANA=300
EXIT_POLICY_PATH=config/exit-policy.json
```

`ENTRY_MODE=off` 关闭研究筛选入口，独立的第三次通知实盘入口由 `THIRD_SIGNAL_EXECUTION_MODE` 控制；后者默认 `simulation`。配置后重新构建并重启服务，随后由本人在 TG 或 Web 点击“启动计数”，不能把重启、状态查询或 `/start` 当作首次实盘启动。个人 GMGN Key、请求签名、SOL 钱包与主网 RPC 仍须配置齐全，具体凭据只留本地。

本策略要求翻倍（+100%）卖出剩余持仓的 50%，跌幅 60% 卖出全部剩余持仓；两条条件随买单显式附加到 GMGN。条件单回读显示 `observed` 只表示供应商报告匹配条件存在，未来自动触发与成交没有因此获得保证。`executionReady` 是本地入口准备情况，不是自动止盈止损已成交的证明。

规则：

- 仅处理 `SCANNER_CHAINS` 允许的链，当前部署为 `solana`。BSC 与 Robinhood 新通知、遗留待处理通知均不参与本轮计数或新开仓分析；历史数据和永久防重记录保留。状态和 Telegram 控制消息显示当前处理链。
- DeBot 与 Ave 分开按“来源 + 链 + 完整 CA”计数，平台累计推送次数不直接导入。
- 启动之后接收的新通知才计数；旧历史回放、重复投递、重复拉取不增加次数或延长有效期。当前只接受发布到接收延迟不超过 120 秒的信号，避免断线补发或匿名延迟数据当作实时通知。
- 新通知使该组过期时间变成接收时间加 6 小时，之前计数保留。例如 0、5、10 小时各来一条，第 10 小时达到第三次。连续 6 小时没有新通知才重新从 1 开始。
- 恰好第三次时检查该通知市值，必须大于零且不超过 100,000 美元。缺失或超过上限会留下明确原因，第四次不会补触发第三次；不使用今日价格/市值补历史决策。
- DeBot 的 `token_trading_stat.mkt_cap` 保存为原始通知市值。只有 `lastUpdateTime` 位于通知之前 120 秒内才作为第三次判断依据；FDV 不替代市值。时间不明仍保存原值，但判断显示未知。
- 按停止后再次启动会新建计数批次；运行中重复点击启动幂等。停止不影响已有持仓监控。
- 每笔买入最多使用对应链原生币总余额的 3%，当前只启用 SOL；金额还会受手续费预留、待结算资金占用和开仓核验约束。不是持有 Meme 的估算总市值的 3%。
- 满足计数、市值、余额和永久防重条件后，仅在准备开仓时读取 GMGN 持仓风险：Top 10 严格大于 25%、捆绑持仓严格大于 40%、老鼠仓严格大于 30%，任一超限不提交买单。等于阈值不因本项拦截。持仓阶段和普通扫描不重复查询这些开仓指标。
- Top 10 使用 `info.stat.top_10_holder_rate`；捆绑和老鼠仓按对应标签钱包的 `amount_percentage` 汇总当前持仓，不能用交易量占比或钱包数量代替。标签列表少于 100 条，或降序列表尾部持仓为零，才视为覆盖正持仓；满 100 条仍有正持仓只作为下界，无法证明未超限时拒绝开仓。缺失、限流、错链错 CA 或超过 30 秒的证据均不当作零风险。
- 保存每次开仓检查的指标、阈值、覆盖范围、时间与拦截原因，Web 和 TG 显示“风控拦截，未提交买单”。GMGN 钓鱼相关 `top_entrapment_trader_percentage` 未确认是当前持仓，仅保存为交易相关参考指标，不虚构持仓比例或额外阈值。

永久防重按“链 + 完整 CA”，EVM 不区分大小写，Solana 保留大小写。两来源、不同钱包、不同运行批次共用该身份。计数库持久记录触发占用与导入的真实历史身份；订单库另有原子永久占用表。达标、提交和成交分别记录：达标本身不是开单成功，只有确认的买入回执才报告成交。模拟候选也不属于真实开仓。

所有历史真实订单（包括已平仓）以及独立测试日志中已提交/结果不明的买入身份均导入。未知提交结果不解锁重试。读取历史失败时拒绝启动计数并显示错误；平仓、6 小时到期、停止启动、服务重启均不清除记录。历史 paper 研究不会被冒充为真实开仓。

Telegram 使用现有机器人，支持 `/count_start`、`/count_stop`、`/count_status` 和对应中文按钮，另有独立的“持仓查询”及分页、手动平仓入口。`/start` 只显示状态和说明，不等同于“启动计数”。只接受配置的本人私聊、有效期 120 秒内且非转发的命令；首次连接丢弃旧指令，更新编号持久去重。Web 与 Telegram 共享同一计数状态。本人启动实盘计数后，达标买入不需要再次手动确认；持仓页的 25%、50%、75%、100% 按钮直接提交所选比例，没有二次确认。通知仍复用原有持久发送队列。

接口（均需原 Dashboard 登录，写入另有同源检查）：

- `GET /dashboard/api/signal-counting?limit=20&offset=0`：状态与分页计数列表。
- `POST /dashboard/api/signal-counting/control`，JSON `{"action":"start"}` 或 `{"action":"stop"}`：按服务配置的策略模式启停计数和后续实盘买入触发；请求不能自行指定其他策略模式。

相关数据为 `data/third-signal-strategy.sqlite`，不得清理永久防重记录。原始历史回放与事后查询补回的历史值分别输出，不混作当时已知数据；采样触及翻倍不等于按止损和真实成交计算的账户胜率。
